# 合集兜底（seasonArchives）接入方案

> 状态：**方案 A 已实施（2026-10-10）**；方案 B 未做；系列链接另行评估
> 调研日期：2026-10-10

> **实施结果**：`src/main/resolver.js` 新增 `parseCollectionLink()` / `isSeriesLink()` /
> `resolveCollection()`，合集页面链接（含 `b23.tv` 分享短链展开后的形式）现已可直接解析。
> `tools/parse-test.js` 增至 **49/49 全绿**（新增「合集页面链接」用例 + 10 项纯函数断言）。

## 一、先说结论

原本我以为是"兜底函数写了没接线"。实测后发现**问题比这更具体、更值得修**：

> **用户从合集页面复制的链接（`collectiondetail?sid=...`），现在会直接报错「未能识别 BV/AV 号」。**

而 `seasonArchives()` 正是为这种链接准备的，只是从没被调用。

## 二、实测现状

| 输入 | 现在的结果 |
|---|---|
| `https://space.bilibili.com/546195/channel/collectiondetail?sid=1903592`（合集页面链接） | ❌ 未能识别 BV/AV 号，请检查链接 |
| `https://space.bilibili.com/546195/channel/seriesdetail?sid=...`（系列页面链接） | ❌ 同上 |
| `https://www.bilibili.com/video/BV1qyNo6TEX3`（合集里某一集的普通视频链接） | ✅ 正常 → 合集 / 22 集 |

补充：**合集分享短链展开后也是 `collectiondetail` 形式**，所以走短链同样失败。

## 三、根因

`src/main/resolver.js` 的 `extractId()` 只认 BV 号与 av 号：

```js
function extractId(text) {
  const m1 = BV_RE.exec(text);        // BVxxxx
  if (m1) return { bvid: m1[1] };
  const m2 = AV_RE.exec(text);        // av123
  if (m2) return { aid: Number(m2[1]) };
  return null;                        // ← 合集链接走到这里
}
```

合集链接里只有 `mid` 和 `sid`，没有 BV 号 → 返回 `null` → 直接抛出「未能识别」。

## 四、方案 A（建议做）：支持合集页面链接

**思路（很轻）**：不必新写一套"合集→下载任务"的构造逻辑，只要**把合集链接「翻译」成一个 BV 号**，后面完全复用现有流程。

1. 识别 `space.bilibili.com/<mid>/channel/collectiondetail?sid=<sid>` → 拿到 `mid` + `sid`；
2. 调**已有的** `bili.seasonArchives(sid, mid)` → 得到该合集的集列表（含 bvid）；
3. 取其中**第一集的 bvid**；
4. 用它走**现有的** `videoDetail()` 流程 —— B站 对合集内任意一集的 `view` 接口都会返回**整个合集**（且 `episodes[]` 里带 cid），后续逻辑一行不用改。

**为什么是 2 次请求就够**（这是关键）：
- 合集接口 `seasons_archives_list` 返回的条目**没有 `cid`**（实测字段：`aid, bvid, title, duration, pubdate, pic …`，无 cid），所以不能直接拿它建任务；
- 但合集内任意一集的 `view` 接口会带回完整 `ugc_season`（含 cid），所以只需"借"第一集的 bvid 作为入口。

**改动点**：

| 文件 | 改动 |
|---|---|
| `src/main/resolver.js` | 新增识别合集链接的正则 + 在 `resolve()` 最前面加一个分支（把 sid 换成 bvid）；`extractId` 不动 |
| `src/renderer/index.html` | 输入提示文案补一句"支持合集链接"（可选） |
| `README.md` | 第 55 行「支持的链接」补上合集链接（可选） |
| `tools/parse-test.js` | **新增**一个用例：合集页面链接 → 期望「合集」 |

**影响面 / 风险：低。** 这是一个**纯新增分支**，只在输入是 `space.bilibili.com/.../collectiondetail` 时触发；所有 BV 号 / av 号 / 普通视频链接走的还是原来那条路，**现有 4 个解析用例不受影响**。

## 五、方案 B（可选，风险较高）：视频链接的合集反查

**场景**：用户粘的是**普通视频链接**，但 `view` 因为未登录 / 风控没返回 `ugc_season`，于是只解析出当前这一集。

**做法**：拿 `owner.mid` → `seasons_series_list` 列该 UP 的全部合集 → **逐个** `seasons_archives_list` 比对，找出含此 bvid 的合集。

**代价与风险**：
- 请求次数多（该 UP 的合集越多越慢）；
- **会改变 BV 链接的既有行为**（原本判定为单视频的，可能变成合集），有误判可能；
- 现有解析测试的语义会被动到。

**建议**：本次先不做。等真的遇到"未登录导致合集漏解析"的反馈，再加（也可以加个设置开关）。

## 六、本次不建议一并做的：系列链接

`seriesdetail?sid=`（系列）走的是**另一套接口**（`x/series/archives`），api.js 里目前没有登记，且它在 `view` 里不体现，需要单独评估。建议先把使用频率更高的**合集链接**支持好，系列单独一期再做。

## 七、收益

- 用户从 B站 合集页面复制链接（含分享短链）即可直接下载整个合集，**不再需要手动找某一集的普通链接**；
- 顺带把 `seasonArchives()` 这个"死代码"接上，不再是备而无用。

## 九、实施记录（2026-10-10）

`src/main/resolver.js`：

- `parseCollectionLink(url)`：用 `new URL()` 解析（参数顺序无关、容忍 `?spm_id_from=…`、
  结尾斜杠），仅认 `bilibili.com` 域下 `/<mid>/channel/collectiondetail`；认不出返回 `null`。
- `isSeriesLink(url)`：`seriesdetail` 走另一套接口，本期未支持，但给出
  「暂不支持「系列」链接，请改用合集链接或视频链接」的明确提示。
- `resolve()`：在 `expandUrl` 之后、`extractId` 之前插入合集分支。
- `resolveCollection(bili, coll)`：
  1. `seasonArchives(sid, mid)` 取集列表；
  2. 取**前 3 个 bvid 依次尝试**（兜住首集被删除 / 转为私密）；
  3. 用入口 bvid **递归调用 `resolve()`**，完全复用普通流程 → 全程 **2 次请求**；
  4. 判定为合集时用 `seasonTitle` 当标题（更贴切）；仅此分支，不影响「粘某集链接」的既有行为。

**验证**：`node tools/_node-shim.js parse-test.js` → **49/49 全绿**
（新增用例 `space.bilibili.com/1027737427/channel/collectiondetail?sid=465513` → 合集 42 集，
与直接粘该合集内某一集链接的结果一致：42 vs 42；原有 4 个用例不受影响）。
